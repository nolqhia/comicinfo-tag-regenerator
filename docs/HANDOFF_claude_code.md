## 1. プロジェクトの目的

自炊した蔵書（Kavita 管理、300 シリーズ）の**ジャンルタグを全再生成**する。

### タグ設計の哲学（最重要・全判断の基準）

1. **接続 (第一目的)**: タグを介して作品同士が意外に繋がること。タグクラウドを回遊して「この二作が同じタグで繋がるのか」という発見が起きる状態を作る。ジャンルの違う作品が要素（場所・職業・モチーフ・現象）で繋がるリンクほど価値が高い。
2. **想起 (第二目的)**: 数年後タイトルを忘れても、覚えている要素から検索で辿り着けること。

両者は同一原理で満たす: **全タグを「他の作品にも原理的に付きうる要素語」にする**。
未来の自分が覚えているのは人名や作中用語ではなく要素の記憶なので、接続可能なタグはそのまま想起にも効く。

### タグ仕様

- 1作品 **10個ちょうど**、日本語 2〜4文字目安（上限6文字、想起力が極めて強い語のみ5〜6文字可）
- **構造タグ5個 + 希少要素タグ5個** が目安（内容優先で ±1 可）
  - 構造タグ = ジャンル・形式の横串（ミステリ, 学園, 叙述トリック…）。既出語彙を再利用し揺れを作らない
  - 希少要素タグ = 作品固有の想起フック。判定は **2冊目テスト**（このタグに2冊目が付く日を想像できるか）
- **禁止**: 作中固有名詞（人名・作中地名・作中造語）、書誌メタ（レーベル・巻数・刊行状態・受賞歴）、英語タグ、タグ内スペース、重複、捏造
  - 作中の架空地名は実在の上位地名に持ち上げる（例: 遠見市→島根）

詳細は `Tag_Prompt_v4.md`（生成プロンプト本体）を参照。

## 2. 現状サマリ（棚卸し済み）

- タグは Kavita の **Genres フィールド**に格納されている（Tags フィールドは空）。書き戻しも Genres 対象。
- 元データ 1393 語彙のうち **73%（1024種）が出現1回**の孤立タグ。接続を生まない死蔵タグの山。
- 正規化により削除92・別名61・複合語分解17（延べ）を整理。**正規化後に3タグ未満へ痩せる破綻作品は0件**。
- 既存タグは「レビューまで読んだ高品質データ」。ゼロ生成でなく**変換の入力として活用**する。

## 4. 全体パイプライン設計

```
[SMB: 自炊 .cbz マスター]  ← source of truth
      │  30 Series ずつローカルへ pull（中断安全のため）
      ▼
[パス1: 自由生成]  台帳を見せず、あらすじ+レビューだけから Qwen3.6 でタグ10個生成
      │            ※アンカリング回避のため意図的に語彙リストを渡さない
      ▼
[集計]  全300作のパス1完了後、生タグ頻度を数え canonical(2+)/pending(1) を確定
      ▼
[パス2: 照合・推敲]  確定台帳で各作の生タグを推敲（揺れ矯正・固有名詞→実在語・複合語分解）
      │              ※初稿後のアンカリングは害でなく推敲材料
      ▼
[検証器(py)]  10個/文字数/重複/discarded混入/揺れ を機械チェック。不合格はリトライ
      ▼
[diff レポート]  旧Genre→新Genre を Series 単位で出力
      │  正規化・固有名詞排除で説明できる差分は「想定内」に自動分類
      │  説明不能な差分のみ人間レビューへ  ★お嬢様の承認ゲート★
      ▼
[書き戻し]  各巻 .cbz 内 ComicInfo.xml の <Genre> を安全置換 → 検証 → SMB へ atomic 差し戻し
```

### 検索パイプラインが品質の天井（最重要の実装判断）

**このタスクの品質を最も左右するのはモデルではなく入力テキストの質。** 検索側に投資すること。

- あらすじ: 楽天ブックス API + OpenBD（構造化・確実）。comicinfo-gen の資産を流用
- レビュー: SearXNG（self-host, CT120 Docker）で `{タイトル} 感想` `{タイトル} ネタバレ 考察` → 上位のフェッチ可能ドメインを trafilatura で本文抽出
- Amazon は robots で弾かれる（実証済み ROBOTS_DISALLOWED）。スクレイプ不可、検索スニペット経由のみ
- 情報が薄い作品は「取得テキスト量が閾値未満ならクエリを替えて最大3回」ループ

## 5. モデル選定（2026-07 時点の結論）

実行環境: Radeon RX 7900 XTX (24GB) / RX 6800 XT (16GB), ROCm。**MLX 版は Apple 専用なので無関係。NVFP4 版は Blackwell 専用なので Radeon 不可。**

| 用途 | モデル | 備考 |
|---|---|---|
| 品質本命（パス2推敲） | `qwen3.6:27b` (dense, 17GB, Q4_K_M) | CJK最上位。24GBに余裕。KVキャッシュ潤沢 |
| 速度枠（パス1量産） | `qwen3.6:35b`＝`35b-a3b` (MoE活性3B, 24GB, Q4) | ※`35b`札はa3bのエイリアス（同一ハッシュ）。denseではない。24GBギリギリ |
| 対抗馬/セカンドオピニオン | `gemma4:31b` (dense, 20GB) | Google系の素直さ。要素抽出の別視点 |

**注意**: Ollama の `qwen3.6:35b` は `35b-a3b`(MoE) の別名。「27bの上位dense」ではない。dense は 27b 系統のみ。
**選定原則**: 最終的には手元10冊で既存タグ（＝正解データ）と突き合わせて決める。体感でなく一致率で判断。

Ollama が Qwen3.6 に未対応の環境では llama.cpp / LM Studio を検索側の受け口にする（要確認）。

## 6. 書き戻し仕様（ComicInfo.xml）

**書き込み先は各 .cbz 内の ComicInfo.xml の `<Genre>`。Kavita API 直書きではない。**
理由: 自炊 .cbz マスターが source of truth。Kavita 再構築・Komga 併用・リーダー移行でもタグが生き残る。

### 実装上の必須注意

1. **`<Genre>` はカンマ区切りの単一要素**。ComicInfo スキーマ（Anansi Project）準拠。
   `<Genre>青春, 学園, 触手</Genre>` の形。`<Tags>` と混同しない。既存は Genres 側なので Genre に統一。
2. **巻ごとに ComicInfo.xml がある**。シリーズ単位のタグでも、物理的には各巻 .cbz 全てに書く。
3. **zip 無劣化の安全書き換え**: ComicInfo.xml だけ差し替え、画像エントリは再圧縮せずコピー。
   元ファイルを直接触らず新規 .cbz を作り、検証後に atomic 差し替え（suji-venator 級の安全志向）。
4. **30 Series バッチ**: SMB 直書きは中断時破損リスク高。SMB→ローカル→書換→検証→書戻しのバッチにし、失敗の影響範囲を30に限定。進捗ログと中断再開を実装。

## 7. 最初にやること（実装前の必須確認）

推測で書き始めない。実環境を1つ確認してから実装に入る。

1. **実 .cbz の ComicInfo.xml を1つ確認**:
   ```bash
   unzip -l "/path/to/sample.cbz"                    # 中に ComicInfo.xml があるか、巻ごとか
   unzip -p "/path/to/sample.cbz" ComicInfo.xml       # 既存タグが <Genre> か <Tags> か
   ```
   ギガ級 .cbz でも xml 抽出だけなら軽い。画像本体は読まない。
2. **SMB マウント形式の確認**: パス、認証、書き込み権限。ローカル pull 先の空き容量（30 Series 分）。
3. **Ollama の Qwen3.6 対応確認**: `ollama pull qwen3.6:27b` が通るか。ダメなら llama.cpp / LM Studio。
4. **既存資産の場所確認**: comicinfo-gen（楽天/OpenBD 呼び出し）、suji-venator（zip 処理の作法）を再利用できるか。

## 9. 運用への移行（再生成完了後）

- 新規取り込み時は「生成 → 台帳照合 → 2件目が来た pending を canonical 昇格 → 台帳更新」を1作ごとに逐次実行。
- 台帳（`seed_vocab.json`）は Kavita の外（SMB上 or citadella git 管理）に置き、生成スクリプトと取り込みスクリプトで共有。
- comicinfo-gen / suji-venator の隣に置き、工具箱として一貫させる。

## 10. 重要な設計判断の記録（なぜそうしたかの根拠）

- **なぜ ComicInfo.xml 書き込みか**: マスターが正。DB直書きは Kavita 一蓮托生になる。
- **なぜ全再生成か**: 73%が孤立タグで接続が死んでいる。揺れ一掃と接続増を一度に達成。破綻0件で安全。
- **なぜ2パス（自由生成→推敲）か**: 事前に語彙を見せるとアンカリングで発想が縮む。初稿後の照合は害がない。
- **なぜ2冊目テストか**: 「将来2冊目が来そうか」の人間直感を、実際に2冊目が来たかで事後確定。固有名詞の暴発を防ぐ。
- **なぜ pending 区画か**: 1件でも良い要素語（触手, 競馬）は将来の接続の種。捨てず保留し2件目で昇格。
- **なぜ検索が天井か**: タグ付けは検索要約タスク。入力が貧しければ大型モデルでも救えない。モデルより検索に投資。
- **なぜ30 Series バッチか**: SMB直書きの破損リスク回避。失敗の影響範囲を限定し diff 承認も現実的な量に。
